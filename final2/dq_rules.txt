Auto Athenium Data Quality Rules
Auto New Business | Collibra review

Rules 1–8 were provided for review and validation. Rules 9–11 are proposed
additions. The notes below use the Athena results reported on November 12, 2026.

Validation findings and decisions

- Data coverage (Rules 1–6 and 11). Randomization history and the source mart
  end on January 26, 2026. Audit history ends on September 15, 2026. Confirm
  which tables receive current data and which completed dates both histories
  should cover before interpreting reconciliation exceptions. Agree on the
  monitoring window for Rules 1, 2, 3 and 5, which scan all available history.
- Transaction matching (Rules 2–4 and 10). Every PSTAR and HUON policy counted
  in Check C had at least one row with a NULL transaction number. Rule 2 uses
  that field in its match. Rules 3 and 4 omit it. Confirm which fields uniquely
  identify a transaction for each source.
- Volume baseline (Rule 6). The dates shown in the sample shifted from daily
  to roughly five-day intervals. Confirm whether the 10 same-weekday dates
  provide a comparable baseline under the current cadence.
- Reviewer checks (Rules 7–8). The reported checks returned zero exceptions.
  Confirm the production schema, the Auto cycle and the number of eligible
  records or groups before interpreting the result.
- Scope (Rules 1–6 and 9–11). The pipeline queries use the tables as provided.
  Confirm that they contain only the intended Auto population before monitoring.

Use dq_rule_validation.sql for the Athena validation queries referenced here.
Run Rules 9–11 against the intended tables before enabling them in Collibra.

Rule 1: Policy Number Completeness

Purpose
Check the final selection history for a missing policy number.

Tables used
uw_analytics.new_business_randomization_hist

What the check does
Returns distinct sets of transaction details when the policy number is NULL or
blank.

Exception
A policy number is NULL or blank.

Expected result
Zero exception rows.

Athena SQL
SELECT DISTINCT
    process_date,
    data_source,
    product,
    transaction_number,
    transaction_term_effective_date,
    transaction_timestamp,
    employeeid
FROM uw_analytics.new_business_randomization_hist
WHERE policynumber IS NULL
   OR TRIM(CAST(policynumber AS VARCHAR)) = ''
ORDER BY process_date DESC, data_source, product;

Rule 2: Selected Policy Exists in Source Mart

Purpose
Verify that each final selection can be traced to the source mart.

Tables used
uw_analytics.new_business_randomization_hist
uw_analytics.new_business_audit_mart_hist

What the check does
Looks for a source mart match on data source, product, policy number,
transaction number, term effective date and transaction timestamp. The search
spans the available source mart history.

Exception
A selected transaction has no matching source mart record on all six fields.

Expected result
Zero exception rows.

Validation note
A NULL transaction number prevents a match under the current SQL. Confirm
whether each source is expected to supply it.

Athena SQL
WITH randomized AS (
    SELECT DISTINCT
        process_date,
        data_source,
        product,
        CAST(policynumber AS VARCHAR) AS policy_number,
        CAST(transaction_number AS VARCHAR) AS transaction_number,
        CAST(transaction_term_effective_date AS DATE) AS term_effective_date,
        CAST(transaction_timestamp AS TIMESTAMP) AS transaction_timestamp
    FROM uw_analytics.new_business_randomization_hist
)
SELECT r.*
FROM randomized r
WHERE NOT EXISTS (
    SELECT 1
    FROM uw_analytics.new_business_audit_mart_hist m
    WHERE m.data_source = r.data_source
      AND m.product = r.product
      AND CAST(m.policynumber AS VARCHAR) = r.policy_number
      AND CAST(m.transaction_number AS VARCHAR) = r.transaction_number
      AND CAST(m.transaction_term_effective_date AS DATE) = r.term_effective_date
      AND CAST(m.transaction_timestamp AS TIMESTAMP) = r.transaction_timestamp
)
ORDER BY r.process_date DESC, r.data_source, r.product, r.policy_number;

Rule 3: Selection Reconciliation

Purpose
Verify that audit history and final selection history agree for each process
date.

Tables used
uw_analytics.new_business_audit_hist
uw_analytics.new_business_randomization_hist

What the check does
Compares distinct 'true' decisions with final selections in both directions.
The match uses process date, data source, product, policy number, term
effective date and transaction timestamp.

Exception
A 'true' decision is missing from final selections, or a final selection has
no matching 'true' decision.

Expected result
Zero exception rows.

Validation note
A NULL in any match field prevents a match. With a NULL policy number on the
audit side, the current query can also label the exception as coming from
randomization. Confirm the shared comparison window and transaction key before
interpreting counts.

Athena SQL
WITH selected AS (
    SELECT DISTINCT
        process_date,
        data_source,
        product,
        CAST(policy_number AS VARCHAR) AS policy_number,
        CAST(term_effective_date AS DATE) AS term_effective_date,
        CAST(transaction_timestamp AS TIMESTAMP) AS transaction_timestamp
    FROM uw_analytics.new_business_audit_hist
    WHERE select_indicator = 'true'
),
randomized AS (
    SELECT DISTINCT
        process_date,
        data_source,
        product,
        CAST(policynumber AS VARCHAR) AS policy_number,
        CAST(transaction_term_effective_date AS DATE) AS term_effective_date,
        CAST(transaction_timestamp AS TIMESTAMP) AS transaction_timestamp
    FROM uw_analytics.new_business_randomization_hist
)
SELECT
    COALESCE(s.process_date, r.process_date) AS process_date,
    COALESCE(s.data_source, r.data_source) AS data_source,
    COALESCE(s.product, r.product) AS product,
    COALESCE(s.policy_number, r.policy_number) AS policy_number,
    COALESCE(s.term_effective_date, r.term_effective_date) AS term_effective_date,
    COALESCE(s.transaction_timestamp, r.transaction_timestamp) AS transaction_timestamp,
    CASE
        WHEN s.policy_number IS NULL THEN 'RANDOMIZATION_WITHOUT_TRUE_SELECTION'
        WHEN r.policy_number IS NULL THEN 'TRUE_SELECTION_MISSING_FROM_RANDOMIZATION'
    END AS dq_issue
FROM selected s
FULL OUTER JOIN randomized r
    ON s.process_date = r.process_date
   AND s.data_source = r.data_source
   AND s.product = r.product
   AND s.policy_number = r.policy_number
   AND s.term_effective_date = r.term_effective_date
   AND s.transaction_timestamp = r.transaction_timestamp
WHERE s.policy_number IS NULL
   OR r.policy_number IS NULL
ORDER BY process_date DESC, dq_issue, data_source, product, policy_number;

Rule 4: Previously Processed Policy Re-entered Selection

Purpose
Check whether a transaction was processed again on the latest audit history
date.

Tables used
uw_analytics.new_business_audit_hist

What the check does
Looks for the same data source, product, policy number, term effective date
and transaction timestamp on an earlier process date. Both 'true' and 'false'
decisions count as processed.

Exception
A transaction on the latest process date also had a decision on an earlier
date.

Expected result
Zero exception rows.

Validation note
Confirm whether a transaction can legitimately re-enter selection after a
'false' decision.

Athena SQL
WITH latest_run AS (
    SELECT MAX(process_date) AS current_process_date
    FROM uw_analytics.new_business_audit_hist
),
current_run AS (
    SELECT DISTINCT
        h.process_date,
        h.data_source,
        h.product,
        CAST(h.policy_number AS VARCHAR) AS policy_number,
        CAST(h.term_effective_date AS DATE) AS term_effective_date,
        CAST(h.transaction_timestamp AS TIMESTAMP) AS transaction_timestamp,
        h.transaction_user,
        h.select_indicator
    FROM uw_analytics.new_business_audit_hist h
    CROSS JOIN latest_run r
    WHERE h.process_date = r.current_process_date
      AND h.select_indicator IN ('true', 'false')
),
prior_history AS (
    SELECT DISTINCT
        h.data_source,
        h.product,
        CAST(h.policy_number AS VARCHAR) AS policy_number,
        CAST(h.term_effective_date AS DATE) AS term_effective_date,
        CAST(h.transaction_timestamp AS TIMESTAMP) AS transaction_timestamp
    FROM uw_analytics.new_business_audit_hist h
    CROSS JOIN latest_run r
    WHERE h.process_date < r.current_process_date
      AND h.select_indicator IN ('true', 'false')
)
SELECT c.*
FROM current_run c
INNER JOIN prior_history p
    ON c.data_source = p.data_source
   AND c.product = p.product
   AND c.policy_number = p.policy_number
   AND c.term_effective_date = p.term_effective_date
   AND c.transaction_timestamp = p.transaction_timestamp
ORDER BY c.data_source, c.product, c.policy_number;

Rule 5: Agent Identifier Completeness

Purpose
Check that each completed selection decision has an agent identifier.

Tables used
uw_analytics.new_business_audit_hist

What the check does
Returns records with a 'true' or 'false' decision where transaction_user, the
agent identifier used in selection, is NULL or blank.

Exception
A completed decision has a NULL or blank agent identifier.

Expected result
Zero exception rows.

Athena SQL
SELECT DISTINCT
    process_date,
    data_source,
    product,
    policy_number,
    term_effective_date,
    transaction_timestamp,
    select_indicator
FROM uw_analytics.new_business_audit_hist
WHERE select_indicator IN ('true', 'false')
  AND (
        transaction_user IS NULL
        OR TRIM(CAST(transaction_user AS VARCHAR)) = ''
      )
ORDER BY process_date DESC, data_source, product, policy_number;

Rule 6: Selected Policy Volume Anomaly by State

Purpose
Flag unusually high or low selection volume by state.

Tables used
uw_analytics.new_business_randomization_hist

What the check does
Counts distinct selected transactions for each state on the latest process
date. The baseline uses the previous 10 same-weekday dates with at least one
selection carrying a populated state. A state with no selections on a baseline
date contributes a zero for that date. The query also uses zero for a baseline
state with no selections on the latest date.

Exception
The current count falls outside the baseline average ± three sample standard
deviations. The lower bound is floored at zero.

Expected result
No ALERT results when the baseline has 10 comparable dates.

Validation note
Fewer than 10 comparable dates yields PASS for states returned, without a
volume comparison. Check the baseline count when interpreting PASS. For
example, an average of 150 and a sample standard deviation of 20 give a range
of 90 to 210.

Athena SQL
WITH current_run AS (
    SELECT MAX(process_date) AS current_process_date
    FROM uw_analytics.new_business_randomization_hist
),
policy_transactions AS (
    SELECT DISTINCT
        process_date,
        state,
        data_source,
        product,
        CAST(policynumber AS VARCHAR) AS policy_number,
        CAST(transaction_number AS VARCHAR) AS transaction_number,
        CAST(transaction_term_effective_date AS DATE) AS term_effective_date,
        CAST(transaction_timestamp AS TIMESTAMP) AS transaction_timestamp
    FROM uw_analytics.new_business_randomization_hist
    WHERE state IS NOT NULL
      AND TRIM(state) <> ''
),
daily_counts AS (
    SELECT
        process_date,
        state,
        COUNT(*) AS selected_policy_count
    FROM policy_transactions
    GROUP BY process_date, state
),
same_weekday_dates AS (
    SELECT process_date
    FROM (
        SELECT
            d.process_date,
            ROW_NUMBER() OVER (ORDER BY d.process_date DESC) AS rn
        FROM (
            SELECT DISTINCT process_date
            FROM daily_counts
        ) d
        CROSS JOIN current_run c
        WHERE d.process_date < c.current_process_date
          AND DAY_OF_WEEK(d.process_date) = DAY_OF_WEEK(c.current_process_date)
    ) x
    WHERE rn <= 10
),
relevant_states AS (
    SELECT DISTINCT d.state
    FROM daily_counts d
    CROSS JOIN current_run c
    WHERE d.process_date = c.current_process_date
    UNION
    SELECT DISTINCT d.state
    FROM daily_counts d
    INNER JOIN same_weekday_dates b
        ON d.process_date = b.process_date
),
history_grid AS (
    SELECT
        b.process_date,
        s.state,
        COALESCE(d.selected_policy_count, 0) AS selected_policy_count
    FROM same_weekday_dates b
    CROSS JOIN relevant_states s
    LEFT JOIN daily_counts d
        ON d.process_date = b.process_date
       AND d.state = s.state
),
baseline AS (
    SELECT
        state,
        COUNT(*) AS baseline_days,
        AVG(CAST(selected_policy_count AS DOUBLE)) AS avg_selected_count,
        STDDEV_SAMP(CAST(selected_policy_count AS DOUBLE)) AS std_selected_count
    FROM history_grid
    GROUP BY state
),
current_counts AS (
    SELECT
        s.state,
        COALESCE(d.selected_policy_count, 0) AS current_selected_count
    FROM relevant_states s
    CROSS JOIN current_run c
    LEFT JOIN daily_counts d
        ON d.process_date = c.current_process_date
       AND d.state = s.state
)
SELECT
    c.current_process_date AS process_date,
    cc.state,
    cc.current_selected_count,
    COALESCE(b.baseline_days, 0) AS baseline_days,
    ROUND(b.avg_selected_count, 2) AS avg_selected_count,
    ROUND(b.std_selected_count, 2) AS std_selected_count,
    ROUND(
        GREATEST(0, b.avg_selected_count - (3 * b.std_selected_count)),
        2
    ) AS lower_threshold,
    ROUND(
        b.avg_selected_count + (3 * b.std_selected_count),
        2
    ) AS upper_threshold,
    CASE
        WHEN COALESCE(b.baseline_days, 0) < 10
             OR b.std_selected_count IS NULL
            THEN 'PASS'
        WHEN cc.current_selected_count
             < GREATEST(0, b.avg_selected_count - (3 * b.std_selected_count))
          OR cc.current_selected_count
             > b.avg_selected_count + (3 * b.std_selected_count)
            THEN 'ALERT'
        ELSE 'PASS'
    END AS dq_status
FROM current_counts cc
CROSS JOIN current_run c
LEFT JOIN baseline b
    ON cc.state = b.state
ORDER BY dq_status DESC, cc.state;

Rule 7: Reviewer Assignment Completeness

Purpose
Check that each record in the latest monthly Auto audit cycle has a primary
reviewer employee ID.

Tables used
insurance_master.policy_audit_transactions_master

What the check does
Finds the latest cycle named Auto YYYY-MM and returns records where
reviewer_1_employee_id is NULL.

Exception
An audit record has a NULL primary reviewer employee ID.

Expected result
Zero exception rows.

Validation note
The query shows up to 100 exceptions. Confirm the schema and populated cycle
before interpreting zero results.

Athena SQL
WITH latest_auto_month AS (
    SELECT MAX(
        REGEXP_EXTRACT(
            region_long_name,
            '^Auto ([0-9]{4}-[0-9]{2})$',
            1
        )
    ) AS cycle_month
    FROM insurance_master.policy_audit_transactions_master
    WHERE REGEXP_LIKE(
        region_long_name,
        '^Auto [0-9]{4}-[0-9]{2}$'
    )
)
SELECT
    a.region_long_name,
    a.policy_number_full,
    a.agent_employee_id,
    a.agent_name,
    a.reviewer_1_username,
    a.reviewer_1_first_name,
    a.reviewer_1_last_name
FROM insurance_master.policy_audit_transactions_master a
CROSS JOIN latest_auto_month c
WHERE a.region_long_name = CONCAT('Auto ', c.cycle_month)
  AND a.reviewer_1_employee_id IS NULL
LIMIT 100;

Rule 8: Agent-to-Reviewer Assignment Consistency

Purpose
Check for agents assigned to multiple primary reviewers on the same assignment
date.

Tables used
insurance_master.policy_audit_transactions_master

What the check does
In the latest Auto YYYY-MM cycle, counts distinct primary reviewer IDs by
agent ID, agent name and reviewer start date. Records must have an agent ID,
reviewer ID and start date to be included.

Exception
An agent ID, agent name and start-date group has more than one primary
reviewer ID.

Expected result
Zero exception rows.

Validation note
Name differences can split records for the same agent and hide a conflict. The
query shows up to 100 exception groups.

Athena SQL
WITH latest_auto_month AS (
    SELECT MAX(
        REGEXP_EXTRACT(
            region_long_name,
            '^Auto ([0-9]{4}-[0-9]{2})$',
            1
        )
    ) AS cycle_month
    FROM insurance_master.policy_audit_transactions_master
    WHERE REGEXP_LIKE(
        region_long_name,
        '^Auto [0-9]{4}-[0-9]{2}$'
    )
)
SELECT
    a.region_long_name,
    a.agent_employee_id,
    a.agent_name,
    a.reviewer_1_start_date,
    COUNT(DISTINCT a.reviewer_1_employee_id) AS reviewer_count,
    ARRAY_AGG(DISTINCT a.reviewer_1_employee_id) AS reviewer_employee_ids,
    COUNT(DISTINCT a.policy_number_full) AS policy_count
FROM insurance_master.policy_audit_transactions_master a
CROSS JOIN latest_auto_month c
WHERE a.region_long_name = CONCAT('Auto ', c.cycle_month)
  AND a.agent_employee_id IS NOT NULL
  AND a.reviewer_1_employee_id IS NOT NULL
  AND a.reviewer_1_start_date IS NOT NULL
GROUP BY
    a.region_long_name,
    a.agent_employee_id,
    a.agent_name,
    a.reviewer_1_start_date
HAVING COUNT(DISTINCT a.reviewer_1_employee_id) > 1
ORDER BY reviewer_count DESC, policy_count DESC
LIMIT 100;

Rule 9: Selection Indicator Validity

Purpose
Flag unexpected decision values that Rules 3–5 would skip.

Tables used
uw_analytics.new_business_audit_hist

What the check does
Returns the process date, unexpected value and affected row count. The allowed
values are the exact strings 'true' and 'false', which were the only values
observed in Check E.

Exception
The selection indicator is NULL or outside the two allowed values.

Expected result
Zero exception rows.

Validation note
Confirm whether audit history can include any valid pending decisions before
using this as a zero-exception check.

Athena SQL
SELECT
    process_date,
    select_indicator,
    COUNT(*) AS row_count
FROM uw_analytics.new_business_audit_hist
WHERE select_indicator IS NULL
   OR select_indicator NOT IN ('true', 'false')
GROUP BY process_date, select_indicator
ORDER BY process_date DESC, select_indicator;

Rule 10: Selection Key Completeness

Purpose
Flag missing fields used to identify, match or compare transactions by run.

Tables used
uw_analytics.new_business_randomization_hist
uw_analytics.new_business_audit_hist

What the check does
Checks process date, data source, product, term effective date and transaction
timestamp in randomization history and for completed decisions in audit
history. It also checks policy number in audit history. Rule 1 covers that
field in randomization history.

Exception
A checked field is NULL, or a checked text identifier is blank after trimming.

Expected result
Zero exception rows.

Validation note
Transaction number is excluded because Check C found at least one missing
value for every PSTAR and HUON policy. Confirm source-specific requirements
separately.

Athena SQL
SELECT DISTINCT
    'randomization_hist' AS table_name,
    process_date,
    data_source,
    product,
    CAST(policynumber AS VARCHAR) AS policy_number,
    CAST(transaction_term_effective_date AS DATE) AS term_effective_date,
    CAST(transaction_timestamp AS TIMESTAMP) AS transaction_timestamp
FROM uw_analytics.new_business_randomization_hist
WHERE process_date IS NULL
   OR data_source IS NULL
   OR TRIM(CAST(data_source AS VARCHAR)) = ''
   OR product IS NULL
   OR TRIM(CAST(product AS VARCHAR)) = ''
   OR transaction_term_effective_date IS NULL
   OR transaction_timestamp IS NULL
UNION ALL
SELECT DISTINCT
    'audit_hist' AS table_name,
    process_date,
    data_source,
    product,
    CAST(policy_number AS VARCHAR) AS policy_number,
    CAST(term_effective_date AS DATE) AS term_effective_date,
    CAST(transaction_timestamp AS TIMESTAMP) AS transaction_timestamp
FROM uw_analytics.new_business_audit_hist
WHERE select_indicator IN ('true', 'false')
  AND (
        process_date IS NULL
        OR data_source IS NULL
        OR TRIM(CAST(data_source AS VARCHAR)) = ''
        OR product IS NULL
        OR TRIM(CAST(product AS VARCHAR)) = ''
        OR policy_number IS NULL
        OR TRIM(CAST(policy_number AS VARCHAR)) = ''
        OR term_effective_date IS NULL
        OR transaction_timestamp IS NULL
      )
ORDER BY process_date DESC, table_name, data_source, product;

Rule 11: Selection Data Freshness

Purpose
Flag tables whose latest available process date may be too old for monitoring.

Tables used
uw_analytics.new_business_audit_mart_hist
uw_analytics.new_business_audit_hist
uw_analytics.new_business_randomization_hist

What the check does
Returns each table with no process dates or with a latest process date more
than seven calendar days before the query date. Seven days is a draft
tolerance.

Exception
The latest process date exceeds the draft tolerance, or the table has no
process dates.

Expected result
Zero exception rows.

Validation note
Check B's reported dates would put all three tables outside the draft
tolerance. Confirm the expected update cadence for each table before setting a
monitoring threshold.

Athena SQL
WITH latest_dates AS (
    SELECT
        'audit_mart_hist' AS table_name,
        CAST(MAX(process_date) AS DATE) AS latest_process_date
    FROM uw_analytics.new_business_audit_mart_hist
    UNION ALL
    SELECT
        'audit_hist',
        CAST(MAX(process_date) AS DATE)
    FROM uw_analytics.new_business_audit_hist
    UNION ALL
    SELECT
        'randomization_hist',
        CAST(MAX(process_date) AS DATE)
    FROM uw_analytics.new_business_randomization_hist
)
SELECT
    table_name,
    latest_process_date,
    DATE_DIFF('day', latest_process_date, CURRENT_DATE) AS days_since_latest
FROM latest_dates
WHERE latest_process_date IS NULL
   OR DATE_DIFF('day', latest_process_date, CURRENT_DATE) > 7
ORDER BY days_since_latest DESC;
