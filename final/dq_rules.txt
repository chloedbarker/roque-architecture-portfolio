Auto Athenium Data Quality Rules for Collibra
Draft data quality checks for the Auto New Business Athenium audit process
Scope
This document defines Auto New Business Athenium data quality checks using the confirmed Auto audit pipeline tables. Each rule is separate, so it can be monitored independently in Collibra. Rules 1-8 are the current rules. Rules 9-11 are proposed additions for review.
Tables used in this draft:
- uw_analytics.new_business_audit_mart_hist
- uw_analytics.new_business_audit_hist
- uw_analytics.new_business_randomization_hist
- insurance_master.policy_audit_transactions_master
Rule 1: Policy Number Completeness
Purpose
Ensure every Auto policy selected for Athenium has a populated policy number.
Tables Used
uw_analytics.new_business_randomization_hist
What the Check Does
Reviews the final selected Auto population and returns distinct policy transactions where the policy number is null or blank.
Failure Condition
Any returned record is a failure.
Expected Result
Zero rows returned.
SQL Query
SELECT DISTINCT
    process_date,
    data_source,
    product,
    transaction_number,
    transaction_term_effective_date,
    transaction_timestamp,
    employeeid
FROM uw_analytics.new_business_randomization_hist
WHERE policynumber IS NULL
   OR TRIM(CAST(policynumber AS VARCHAR)) = ''
ORDER BY process_date DESC, data_source, product;
Notes / Threshold
Hard DQ rule. Threshold = 0 failures.
Rule 2: Selected Policy Exists in Source Mart
Purpose
Ensure every policy transaction in the final Auto randomization history can be traced back to the Auto audit source mart history.
Tables Used
uw_analytics.new_business_randomization_hist; uw_analytics.new_business_audit_mart_hist
What the Check Does
Creates a distinct policy-transaction population from randomization history and checks for a matching source record using source, product, policy number, transaction number, term effective date, and transaction timestamp.
Failure Condition
A selected policy transaction has no matching record in the source mart history.
Expected Result
Zero rows returned.
SQL Query
WITH randomized AS (
    SELECT DISTINCT
        process_date,
        data_source,
        product,
        CAST(policynumber AS VARCHAR) AS policy_number,
        CAST(transaction_number AS VARCHAR) AS transaction_number,
        CAST(transaction_term_effective_date AS DATE) AS term_effective_date,
        CAST(transaction_timestamp AS TIMESTAMP) AS transaction_timestamp
    FROM uw_analytics.new_business_randomization_hist
)
SELECT r.*
FROM randomized r
WHERE NOT EXISTS (
    SELECT 1
    FROM uw_analytics.new_business_audit_mart_hist m
    WHERE m.data_source = r.data_source
      AND m.product = r.product
      AND CAST(m.policynumber AS VARCHAR) = r.policy_number
      AND CAST(m.transaction_number AS VARCHAR) = r.transaction_number
      AND CAST(m.transaction_term_effective_date AS DATE) = r.term_effective_date
      AND CAST(m.transaction_timestamp AS TIMESTAMP) = r.transaction_timestamp
)
ORDER BY r.process_date DESC, r.data_source, r.product, r.policy_number;
Notes / Threshold
Hard DQ rule. Threshold = 0 failures.
Rule 3: Selection Reconciliation
Purpose
Ensure the policy transactions marked as selected in audit history reconcile to the policy transactions persisted in randomization history.
Tables Used
uw_analytics.new_business_audit_hist; uw_analytics.new_business_randomization_hist
What the Check Does
Compares distinct select_indicator = true policy transactions in audit history with distinct policy transactions in randomization history for the same process date. The comparison is based on the policy-transaction identity; agent completeness is checked separately.
Failure Condition
A true selection is missing from randomization history, or a randomization history policy does not have a matching true selection.
Expected Result
Zero rows returned.
SQL Query
WITH selected AS (
    SELECT DISTINCT
        process_date,
        data_source,
        product,
        CAST(policy_number AS VARCHAR) AS policy_number,
        CAST(term_effective_date AS DATE) AS term_effective_date,
        CAST(transaction_timestamp AS TIMESTAMP) AS transaction_timestamp
    FROM uw_analytics.new_business_audit_hist
    WHERE select_indicator = 'true'
),
randomized AS (
    SELECT DISTINCT
        process_date,
        data_source,
        product,
        CAST(policynumber AS VARCHAR) AS policy_number,
        CAST(transaction_term_effective_date AS DATE) AS term_effective_date,
        CAST(transaction_timestamp AS TIMESTAMP) AS transaction_timestamp
    FROM uw_analytics.new_business_randomization_hist
)
SELECT
    COALESCE(s.process_date, r.process_date) AS process_date,
    COALESCE(s.data_source, r.data_source) AS data_source,
    COALESCE(s.product, r.product) AS product,
    COALESCE(s.policy_number, r.policy_number) AS policy_number,
    COALESCE(s.term_effective_date, r.term_effective_date) AS term_effective_date,
    COALESCE(s.transaction_timestamp, r.transaction_timestamp) AS transaction_timestamp,
    CASE
        WHEN s.policy_number IS NULL THEN 'RANDOMIZATION_WITHOUT_TRUE_SELECTION'
        WHEN r.policy_number IS NULL THEN 'TRUE_SELECTION_MISSING_FROM_RANDOMIZATION'
    END AS dq_issue
FROM selected s
FULL OUTER JOIN randomized r
    ON s.process_date = r.process_date
   AND s.data_source = r.data_source
   AND s.product = r.product
   AND s.policy_number = r.policy_number
   AND s.term_effective_date = r.term_effective_date
   AND s.transaction_timestamp = r.transaction_timestamp
WHERE s.policy_number IS NULL
   OR r.policy_number IS NULL
ORDER BY process_date DESC, dq_issue, data_source, product, policy_number;
Notes / Threshold
Hard DQ rule. Threshold = 0 reconciliation differences.
Rule 4: Previously Processed Policy Re-entered Selection
Purpose
Ensure a policy transaction processed in the current audit-selection run was not already processed in an earlier run.
Tables Used
uw_analytics.new_business_audit_hist
What the Check Does
Identifies the latest process date, builds the distinct current-run policy-transaction population, and checks each transaction against all prior audit-selection history. The comparison intentionally does not use the agent identifier, so a missing agent value cannot allow the same transaction to bypass the duplicate check.
Failure Condition
A policy transaction in the current process date also exists on an earlier process date.
Expected Result
Zero rows returned.
SQL Query
WITH latest_run AS (
    SELECT MAX(process_date) AS current_process_date
    FROM uw_analytics.new_business_audit_hist
),
current_run AS (
    SELECT DISTINCT
        h.process_date,
        h.data_source,
        h.product,
        CAST(h.policy_number AS VARCHAR) AS policy_number,
        CAST(h.term_effective_date AS DATE) AS term_effective_date,
        CAST(h.transaction_timestamp AS TIMESTAMP) AS transaction_timestamp,
        h.transaction_user,
        h.select_indicator
    FROM uw_analytics.new_business_audit_hist h
    CROSS JOIN latest_run r
    WHERE h.process_date = r.current_process_date
      AND h.select_indicator IN ('true', 'false')
),
prior_history AS (
    SELECT DISTINCT
        h.data_source,
        h.product,
        CAST(h.policy_number AS VARCHAR) AS policy_number,
        CAST(h.term_effective_date AS DATE) AS term_effective_date,
        CAST(h.transaction_timestamp AS TIMESTAMP) AS transaction_timestamp
    FROM uw_analytics.new_business_audit_hist h
    CROSS JOIN latest_run r
    WHERE h.process_date < r.current_process_date
      AND h.select_indicator IN ('true', 'false')
)
SELECT c.*
FROM current_run c
INNER JOIN prior_history p
    ON c.data_source = p.data_source
   AND c.product = p.product
   AND c.policy_number = p.policy_number
   AND c.term_effective_date = p.term_effective_date
   AND c.transaction_timestamp = p.transaction_timestamp
ORDER BY c.data_source, c.product, c.policy_number;
Notes / Threshold
Hard DQ rule. Threshold = 0 previously processed policy transactions in the current run.
Rule 5: Agent Identifier Completeness
Purpose
Ensure every Auto policy that completes a true/false randomization decision has the agent identifier required by the selection process.
Tables Used
uw_analytics.new_business_audit_hist
What the Check Does
Reviews policies that received a true or false selection decision and returns records where transaction_user is null or blank. In the Auto selection history, transaction_user carries the agent identifier used by the randomization process. A missing value can prevent prior selections from being matched correctly on later runs.
Failure Condition
A policy transaction that completed a true/false selection decision has no populated agent identifier.
Expected Result
Zero rows returned.
SQL Query
SELECT DISTINCT
    process_date,
    data_source,
    product,
    policy_number,
    term_effective_date,
    transaction_timestamp,
    select_indicator
FROM uw_analytics.new_business_audit_hist
WHERE select_indicator IN ('true', 'false')
  AND (
        transaction_user IS NULL
        OR TRIM(CAST(transaction_user AS VARCHAR)) = ''
      )
ORDER BY process_date DESC, data_source, product, policy_number;
Notes / Threshold
Hard DQ rule. Threshold = 0 failures.
Rule 6: Selected Policy Volume Anomaly by State
Purpose
Identify unusually high or low Auto Athenium selected-policy volume by state using each state's own recent history.
Tables Used
uw_analytics.new_business_randomization_hist
What the Check Does
Counts distinct selected policy transactions by process date and state. The most recent process date is treated as the current run. The historical baseline uses the previous 10 process dates that fall on the same day of the week as the current run. For example, a Monday run is compared with the prior 10 Mondays, while a Sunday run is compared with the prior 10 Sundays. For each state, the query calculates the average and sample standard deviation across those 10 comparable process dates and flags the current count when it falls outside average plus or minus three standard deviations. A state with no selected policies on one of the 10 baseline dates is counted as zero for that date.
Failure Condition
The current selected-policy count is above average + 3 standard deviations or below average - 3 standard deviations, after 10 prior same-weekday process dates are available.
Expected Result
No alerts. If fewer than 10 prior same-weekday process dates are available, the check passes without triggering an alert.
SQL Query
WITH current_run AS (
    SELECT MAX(process_date) AS current_process_date
    FROM uw_analytics.new_business_randomization_hist
),
policy_transactions AS (
    SELECT DISTINCT
        process_date,
        state,
        data_source,
        product,
        CAST(policynumber AS VARCHAR) AS policy_number,
        CAST(transaction_number AS VARCHAR) AS transaction_number,
        CAST(transaction_term_effective_date AS DATE) AS term_effective_date,
        CAST(transaction_timestamp AS TIMESTAMP) AS transaction_timestamp
    FROM uw_analytics.new_business_randomization_hist
    WHERE state IS NOT NULL
      AND TRIM(state) <> ''
),
daily_counts AS (
    SELECT
        process_date,
        state,
        COUNT(*) AS selected_policy_count
    FROM policy_transactions
    GROUP BY process_date, state
),
same_weekday_dates AS (
    SELECT process_date
    FROM (
        SELECT
            d.process_date,
            ROW_NUMBER() OVER (ORDER BY d.process_date DESC) AS rn
        FROM (
            SELECT DISTINCT process_date
            FROM daily_counts
        ) d
        CROSS JOIN current_run c
        WHERE d.process_date < c.current_process_date
          AND DAY_OF_WEEK(d.process_date) = DAY_OF_WEEK(c.current_process_date)
    ) x
    WHERE rn <= 10
),
relevant_states AS (
    SELECT DISTINCT d.state
    FROM daily_counts d
    CROSS JOIN current_run c
    WHERE d.process_date = c.current_process_date
    UNION
    SELECT DISTINCT d.state
    FROM daily_counts d
    INNER JOIN same_weekday_dates b
        ON d.process_date = b.process_date
),
history_grid AS (
    SELECT
        b.process_date,
        s.state,
        COALESCE(d.selected_policy_count, 0) AS selected_policy_count
    FROM same_weekday_dates b
    CROSS JOIN relevant_states s
    LEFT JOIN daily_counts d
        ON d.process_date = b.process_date
       AND d.state = s.state
),
baseline AS (
    SELECT
        state,
        COUNT(*) AS baseline_days,
        AVG(CAST(selected_policy_count AS DOUBLE)) AS avg_selected_count,
        STDDEV_SAMP(CAST(selected_policy_count AS DOUBLE)) AS std_selected_count
    FROM history_grid
    GROUP BY state
),
current_counts AS (
    SELECT
        s.state,
        COALESCE(d.selected_policy_count, 0) AS current_selected_count
    FROM relevant_states s
    CROSS JOIN current_run c
    LEFT JOIN daily_counts d
        ON d.process_date = c.current_process_date
       AND d.state = s.state
)
SELECT
    c.current_process_date AS process_date,
    cc.state,
    cc.current_selected_count,
    COALESCE(b.baseline_days, 0) AS baseline_days,
    ROUND(b.avg_selected_count, 2) AS avg_selected_count,
    ROUND(b.std_selected_count, 2) AS std_selected_count,
    ROUND(
        GREATEST(0, b.avg_selected_count - (3 * b.std_selected_count)),
        2
    ) AS lower_threshold,
    ROUND(
        b.avg_selected_count + (3 * b.std_selected_count),
        2
    ) AS upper_threshold,
    CASE
        WHEN COALESCE(b.baseline_days, 0) < 10
             OR b.std_selected_count IS NULL
            THEN 'PASS'
        WHEN cc.current_selected_count
             < GREATEST(0, b.avg_selected_count - (3 * b.std_selected_count))
          OR cc.current_selected_count
             > b.avg_selected_count + (3 * b.std_selected_count)
            THEN 'ALERT'
        ELSE 'PASS'
    END AS dq_status
FROM current_counts cc
CROSS JOIN current_run c
LEFT JOIN baseline b
    ON cc.state = b.state
ORDER BY dq_status DESC, cc.state;
Notes / Threshold
Monitoring DQ rule. Use the previous 10 process dates that fall on the same day of the week as the current run. Calculate the state-level average and sample standard deviation across those 10 comparable dates. Alert when the current state volume falls outside the historical average +/- 3 standard deviations. If fewer than 10 prior same-weekday process dates are available, the check passes without triggering an alert.
How the Standard Deviation Threshold Is Derived
Standard deviation measures how much selected-policy volume varies around its average for comparable runs. A small standard deviation means the state is usually stable on that day of the week. A larger standard deviation means the state naturally has wider swings. The SQL calculates the sample standard deviation with STDDEV_SAMP using the prior 10 same-weekday process-date counts for each state.
The baseline is derived in four steps: (1) identify the current run day of the week, (2) select the previous 10 process dates with that same weekday, (3) calculate each state's average and sample standard deviation across those 10 counts, and (4) compare the current state count with average +/- 3 standard deviations. In statistical terms, sample standard deviation is the square root of the sum of squared differences from the average divided by n - 1. The SQL performs this calculation through STDDEV_SAMP.
Lower threshold = same-weekday average - (3 x standard deviation)
Upper threshold = same-weekday average + (3 x standard deviation)
Example
Assume the current process date is a Monday. The query retrieves the previous 10 Mondays for Texas.
Average of the prior 10 Monday counts = 150
Sample standard deviation of those 10 Monday counts = 20
A standard deviation of 20 means the historical Monday counts typically vary around the 150 average by about 20 policies. The monitoring range uses three standard deviations:
Lower threshold = 150 - (3 x 20) = 90
Upper threshold = 150 + (3 x 20) = 210
If the current Monday Texas count is 155, it falls between 90 and 210, so the result is PASS.
If the current Monday Texas count is 225, it is above 210, so the result is ALERT for unusually high volume.
If the current Monday Texas count is 70, it is below 90, so the result is ALERT for unusually low volume.
The same logic applies automatically to every day of the week. A Saturday run uses the prior 10 Saturdays; a Sunday run uses the prior 10 Sundays. If fewer than 10 prior matching weekdays exist, the rule returns PASS and does not alert.
Rule 7: Reviewer Assignment Completeness
Purpose
Ensure every policy in the current Auto monthly audit population has a populated primary reviewer employee ID.
Tables Used
insurance_master.policy_audit_transactions_master
What the Check Does
Identifies the latest monthly Auto audit cycle using region_long_name values in the format Auto YYYY-MM and returns policies where reviewer_1_employee_id is null. The monthly pattern intentionally excludes AO, quarterly, targeted, and other Auto audit populations.
Failure Condition
A policy in the latest monthly Auto audit cycle does not have a populated reviewer_1_employee_id.
Expected Result
Zero rows returned.
SQL Query
WITH latest_auto_month AS (
    SELECT MAX(
        REGEXP_EXTRACT(
            region_long_name,
            '^Auto ([0-9]{4}-[0-9]{2})$',
            1
        )
    ) AS cycle_month
    FROM insurance_master.policy_audit_transactions_master
    WHERE REGEXP_LIKE(
        region_long_name,
        '^Auto [0-9]{4}-[0-9]{2}$'
    )
)
SELECT
    a.region_long_name,
    a.policy_number_full,
    a.agent_employee_id,
    a.agent_name,
    a.reviewer_1_username,
    a.reviewer_1_first_name,
    a.reviewer_1_last_name
FROM insurance_master.policy_audit_transactions_master a
CROSS JOIN latest_auto_month c
WHERE a.region_long_name = CONCAT('Auto ', c.cycle_month)
  AND a.reviewer_1_employee_id IS NULL
LIMIT 100;
Notes / Threshold
Hard DQ rule. Threshold = 0 failures. The rule evaluates the latest monthly Auto cycle rather than historical cycles because older records can contain reviewer username/name information even when the employee ID was not populated.
Rule 8: Agent-to-Reviewer Assignment Consistency
Purpose
Ensure policies for the same agent are assigned consistently to one primary reviewer for the same Auto audit assignment date.
Tables Used
insurance_master.policy_audit_transactions_master
What the Check Does
For the latest monthly Auto audit cycle, groups policies by agent and reviewer start date and counts distinct reviewer_1_employee_id values. The rule flags an agent/date combination when policies for that agent are assigned to more than one primary reviewer.
Failure Condition
The same agent has more than one reviewer_1_employee_id on the same reviewer_1_start_date within the latest monthly Auto audit cycle.
Expected Result
Zero rows returned.
SQL Query
WITH latest_auto_month AS (
    SELECT MAX(
        REGEXP_EXTRACT(
            region_long_name,
            '^Auto ([0-9]{4}-[0-9]{2})$',
            1
        )
    ) AS cycle_month
    FROM insurance_master.policy_audit_transactions_master
    WHERE REGEXP_LIKE(
        region_long_name,
        '^Auto [0-9]{4}-[0-9]{2}$'
    )
)
SELECT
    a.region_long_name,
    a.agent_employee_id,
    a.agent_name,
    a.reviewer_1_start_date,
    COUNT(DISTINCT a.reviewer_1_employee_id) AS reviewer_count,
    ARRAY_AGG(DISTINCT a.reviewer_1_employee_id) AS reviewer_employee_ids,
    COUNT(DISTINCT a.policy_number_full) AS policy_count
FROM insurance_master.policy_audit_transactions_master a
CROSS JOIN latest_auto_month c
WHERE a.region_long_name = CONCAT('Auto ', c.cycle_month)
  AND a.agent_employee_id IS NOT NULL
  AND a.reviewer_1_employee_id IS NOT NULL
  AND a.reviewer_1_start_date IS NOT NULL
GROUP BY
    a.region_long_name,
    a.agent_employee_id,
    a.agent_name,
    a.reviewer_1_start_date
HAVING COUNT(DISTINCT a.reviewer_1_employee_id) > 1
ORDER BY reviewer_count DESC, policy_count DESC
LIMIT 100;
Notes / Threshold
Hard DQ rule. Threshold = 0 inconsistent agent-to-reviewer assignments. Reviewer assignments can legitimately change over time, so the rule does not require one reviewer per agent across an entire month or across historical audit cycles.

Rule 9: Selection Data Freshness (Proposed)
Purpose
Check that new Auto selection records arrive on schedule. If a load is missing, Rule 6 can still report volume for an older date because it evaluates the latest date available.
Tables Used
uw_analytics.new_business_randomization_hist
What the Check Does
Finds the most recent process_date in randomization history and calculates its age in calendar days. Returns one exception if the date is missing or exceeds the allowance.
Failure Condition
Randomization history has no populated process date, or the latest date is more than 1 calendar day before the current date.
Expected Result
Zero rows returned.
SQL Query
WITH latest_selection AS (
    SELECT MAX(CAST(process_date AS DATE)) AS latest_process_date
    FROM uw_analytics.new_business_randomization_hist
)
SELECT
    latest_process_date,
    DATE_DIFF('day', latest_process_date, CURRENT_DATE) AS days_since_latest_selection,
    CASE
        WHEN latest_process_date IS NULL THEN 'NO_SELECTION_DATE'
        ELSE 'STALE_SELECTION_DATA'
    END AS dq_issue
FROM latest_selection
WHERE latest_process_date IS NULL
   OR DATE_DIFF('day', latest_process_date, CURRENT_DATE) > 1;
Notes / Threshold
Proposed monitoring rule. The 1-day allowance is a draft for a daily schedule that produces selection records. Confirm the schedule, business date and load deadline with Check A and the run owner. Use the run log to distinguish a successful run with zero selections from a missed load, and confirm whether an existing monitor already covers job completion.
Rule 10: Selected Policy Reaches Audit Tracking (Proposed)
Purpose
Verify that selected policies reach the audit team's work list. Rules 2 and 3 check the pipeline up to randomization history. This proposal checks the next handoff to audit tracking.
Tables Used
uw_analytics.new_business_randomization_hist; insurance_master.policy_audit_transactions_master
What the Check Does
Reviews distinct selection date, source, product and policy combinations from 30 to 60 calendar days ago, inclusive. The draft returns combinations for which the policy number has no match anywhere in the audit master.
Failure Condition
A selection old enough to have reached audit tracking has no matching record for the expected audit cycle or work item. The draft checks policy-number presence to explore that gap.
Expected Result
Zero rows returned.
SQL Query
WITH selected AS (
    SELECT DISTINCT
        CAST(process_date AS DATE) AS process_date,
        data_source,
        product,
        TRIM(CAST(policynumber AS VARCHAR)) AS policy_number
    FROM uw_analytics.new_business_randomization_hist
    WHERE CAST(process_date AS DATE)
          BETWEEN CURRENT_DATE - INTERVAL '60' DAY
              AND CURRENT_DATE - INTERVAL '30' DAY
      AND NULLIF(TRIM(CAST(policynumber AS VARCHAR)), '') IS NOT NULL
)
SELECT s.*
FROM selected s
WHERE NOT EXISTS (
    SELECT 1
    FROM insurance_master.policy_audit_transactions_master a
    WHERE TRIM(CAST(a.policy_number AS VARCHAR)) = s.policy_number
)
ORDER BY s.process_date DESC, s.data_source, s.product, s.policy_number;
Notes / Threshold
Proposed threshold = 0 missing handoffs once the key, scope and deadline are confirmed. Use Check F to compare policy-number fields and verify known matches with the audit owner. Add the approved audit population and cycle or work-item match before monitoring. An unrelated audit for the same policy can satisfy the draft match. Use Check G to compare observed coverage by age, and use the process deadline or confirmed audit-entry timestamps to set the window. The draft excludes blank and NULL policy numbers because Rule 1 covers them. Review exceptions before they age out of the window.

Rule 11: Reviewer Is Not the Policy's Agent (Proposed)
Purpose
Protect audit independence by identifying assignments where the primary reviewer is the same employee as the agent whose work is being reviewed.
Tables Used
insurance_master.policy_audit_transactions_master
What the Check Does
Using the same latest monthly Auto cycle as Rules 7 and 8, compares populated reviewer and agent employee IDs after trimming spaces and returns matching pairs.
Failure Condition
A policy in the latest monthly Auto audit cycle is assigned to its own agent for review.
Expected Result
Zero rows returned.
SQL Query
WITH latest_auto_month AS (
    SELECT MAX(
        REGEXP_EXTRACT(
            region_long_name,
            '^Auto ([0-9]{4}-[0-9]{2})$',
            1
        )
    ) AS cycle_month
    FROM insurance_master.policy_audit_transactions_master
    WHERE REGEXP_LIKE(
        region_long_name,
        '^Auto [0-9]{4}-[0-9]{2}$'
    )
)
SELECT
    a.region_long_name,
    a.policy_number_full,
    a.agent_employee_id,
    a.agent_name,
    a.reviewer_1_employee_id,
    a.reviewer_1_first_name,
    a.reviewer_1_last_name
FROM insurance_master.policy_audit_transactions_master a
CROSS JOIN latest_auto_month c
WHERE a.region_long_name = CONCAT('Auto ', c.cycle_month)
  AND NULLIF(TRIM(CAST(a.agent_employee_id AS VARCHAR)), '')
      = NULLIF(TRIM(CAST(a.reviewer_1_employee_id AS VARCHAR)), '')
ORDER BY a.agent_employee_id, a.policy_number_full;
Notes / Threshold
Proposed threshold = 0 self-review assignments if the business prohibits them. Confirm that both fields use the same employee ID system and that the agent field identifies the person whose work is being audited. Check H profiles the IDs, and the audit owner can confirm their meaning and any exceptions. Blank and NULL IDs fall outside the comparison.
Implementation Notes for Collibra
- Reviewer assignment rules (Rules 7, 8 and 11) use the latest monthly Auto cycle (Auto YYYY-MM) and intentionally exclude AO, quarterly, targeted, and other audit populations.
- Each hard DQ query is written so that returned rows represent failures. A successful run returns zero rows.
- The volume anomaly rule is monitoring-oriented. It returns the current count, same-weekday baseline average, standard deviation, thresholds, and PASS/ALERT status for Collibra monitoring.
- Counts for the volume rule are based on distinct policy transactions, not raw randomization-history rows, because Auto policy detail can produce multiple rows for the same selected policy transaction. A missing state count on a baseline date is treated as zero for that state.
- Review Rule 9 before interpreting checks that depend on current randomization data. Confirm each table's own date or cycle when interpreting the other rules.
Review Notes on Rules 1-8
These are observations from reviewing the queries. They have not been confirmed against live results, and the rule SQL above is unchanged. The checks below each note are in the Pre-Implementation Checks section.
- Rules 1, 2, 3 and 5: These scan all history, while Rules 4 and 6 use the latest available process date and Rules 7 and 8 use the latest available Auto cycle. With a threshold of 0, an old exception can keep triggering while it remains in scope. Should monitoring use a common completed run or another agreed window? (Check B)
- Rules 1-6: The purpose says Auto, but the SQL has no product filter. Are the uw_analytics tables Auto-only? (Check D)
- Rule 2: transaction_number is part of the match. NULL never equals NULL, so a selected transaction with a NULL transaction number always fails, even if it exists in the source. How many selected policies have a NULL transaction number, and which sources expect one? Use Check C to establish the count.
- Rule 3: The comparison has no date filter. If the two tables cover different date ranges, every date outside the overlap shows up as a difference. (Check B)
- Rules 3, 4 and 5: The SQL compares select_indicator to the lowercase text 'true' and 'false'. Confirm the actual stored values. (Check E)
- Rule 4: Both true and false decisions count as processed. Is re-entry after a false decision ever allowed?
- Rule 6: When average - 3 x standard deviation is below zero, the lower threshold becomes 0, so a low-volume state can drop to zero without alerting. Fewer than 10 baseline days also returns PASS. INSUFFICIENT_HISTORY would make that visible. An absent expected run can go undetected because the check uses the latest available date. Proposed Rule 9 adds a data-age check.
- Rules 7 and 8: LIMIT 100 caps the exceptions returned. Does Collibra count the returned rows? If so, use the uncapped count for monitoring and keep a capped version for sampling. (Check J)
- Rule 7: The rule checks NULL but not blank, unlike Rules 1 and 5. Is there a grace period between cycle creation and reviewer assignment?
- Rule 8: agent_name is in the GROUP BY. If one agent ID has two name spellings, it splits into two groups and can hide a conflict. Should the check group by agent ID within the same cycle and assignment date, with the name used only for display?
- Rules 7, 8, 10 and 11: These use insurance_master, while table exploration used insurance_master_prod. Which schema should Collibra point to? (Check I)

Check F: Which Policy Number Field Matches (Rule 10)
WITH selected AS (
    SELECT DISTINCT TRIM(CAST(policynumber AS VARCHAR)) AS policy_number
    FROM uw_analytics.new_business_randomization_hist
    WHERE CAST(process_date AS DATE)
          BETWEEN CURRENT_DATE - INTERVAL '60' DAY
              AND CURRENT_DATE - INTERVAL '30' DAY
      AND NULLIF(TRIM(CAST(policynumber AS VARCHAR)), '') IS NOT NULL
),
audit_policy_number AS (
    SELECT DISTINCT TRIM(CAST(policy_number AS VARCHAR)) AS policy_number
    FROM insurance_master.policy_audit_transactions_master
),
audit_policy_number_full AS (
    SELECT DISTINCT TRIM(CAST(policy_number_full AS VARCHAR)) AS policy_number
    FROM insurance_master.policy_audit_transactions_master

       FROM selected s
       INNER JOIN audit_policy_number a ON s.policy_number = a.policy_number) AS matched_on_policy_number,
    (SELECT COUNT(*)
       FROM selected s
       INNER JOIN audit_policy_number_full a ON s.policy_number = a.policy_number) AS matched_on_policy_number_full;
What to look for: Compare coverage for both fields, then verify known selections against the expected Auto audit cycle or work item. A higher match count can include unrelated audits. A low count can reflect format, scope, timing or incomplete coverage.
Check G: Audit Tracking Match Coverage by Selection Age (Rule 10)
WITH selected AS (
    SELECT DISTINCT
        CAST(process_date AS DATE) AS process_date,
        TRIM(CAST(policynumber AS VARCHAR)) AS policy_number
    FROM uw_analytics.new_business_randomization_hist
    WHERE CAST(process_date AS DATE)
          BETWEEN CURRENT_DATE - INTERVAL '120' DAY AND CURRENT_DATE
      AND NULLIF(TRIM(CAST(policynumber AS VARCHAR)), '') IS NOT NULL
),
audit_keys AS (
    SELECT DISTINCT TRIM(CAST(policy_number AS VARCHAR)) AS policy_number
    FROM insurance_master.policy_audit_transactions_master
),
aged AS (
    SELECT
        DATE_DIFF('day', s.process_date, CURRENT_DATE) / 30 AS age_bucket_30_days,
        CASE WHEN a.policy_number IS NOT NULL THEN 1 ELSE 0 END AS found_in_audit
    FROM selected s
    LEFT JOIN audit_keys a
        ON s.policy_number = a.policy_number
)
SELECT
    age_bucket_30_days,
    COUNT(*) AS selected_policy_date_pairs,
    SUM(found_in_audit) AS found_in_audit,
    ROUND(100.0 * SUM(found_in_audit) / COUNT(*), 1) AS pct_found
FROM aged
GROUP BY age_bucket_30_days
ORDER BY age_bucket_30_days;
What to look for: Bucket 0 covers 0-29 days, bucket 1 covers 30-59 days, and so on. pct_found is the share of selection date and policy pairs with any audit-master match today. Use the approved key and audit scope after Check F. Use a confirmed audit-entry timestamp or the business deadline to assess time to tracking.
